01Objective and reviewed scope

Determine how closely NT.QAMS complies with the Enterprise Application Architecture checklist and the project's own "law" (CLAUDE.md, ADRs, SRS). The system is a regulated multi-tenant QMS targeting ISO/IEC 17025, ISO 15189, ISO 9001, 21 CFR Part 11, and EU GMP Annex 11.

Compliance was not inferred from folder names, interfaces, comments, or prior self-audits. Behavior was validated against concrete artifacts: project references, the DbContext, interceptors, migrations, middleware, MediatR handlers/behaviors, ADRs, and the test-suite source. Evidence is cited as file:line throughout.

06Executive summary

NT.QAMS is an unusually mature, defense-in-depth, and honestly-documented enterprise application that has clearly been through multiple remediation cycles. Its strongest controls are implemented as layered, testable, fail-closed mechanisms rather than single points of trust, and several are enforced as build-time CI gates (deny-by-default command policy, module boundaries, API-surface snapshot).

The audit found zero CRITICAL findings and no cross-tenant data-exposure path. Tenant isolation is genuinely triple-layered — EF global query filter + PostgreSQL FORCE ROW LEVEL SECURITY + a NOSUPERUSER NOBYPASSRLS runtime role — reinforced by tenant-composite foreign keys and a boot-time role guard that refuses to start if the DB role could bypass RLS. It is exercised by cross-tenant denial tests against real PostgreSQL with the EF filter deliberately disabled.

The material gaps are not in the headline security architecture but in completeness and consistency at the edges: broken object-level authorization on file downloads (within a tenant), an e-signature record that binds the signed record's version only in free text, a JWT lifetime that contradicts its governing ADR, primitive-obsession where the domain documents ~30 value objects but implements ~1, no enforced transaction boundary, and specific test holes (validators, migration-drift, value-objects). The named "Serilog" observability standard is met in spirit by structured Microsoft.Extensions.Logging JSON, not Serilog itself.

Verified strengths (evidence-backed, not assumed) Multi-tenant isolation (EF filter + FORCE RLS + NOBYPASSRLS role + tenant-composite FKs + boot guard + real-PG denial tests) · deny-by-default authorization at build & runtime · Clean Architecture enforced by NetArchTest · append-only hash-chained audit ledger with a tamper test · xmin optimistic concurrency · transactional outbox with dead-letter/backoff/SKIP-LOCKED · fully-validated JWT + rotating replay-resistant refresh cookie · ConfigGuard fail-fast · unusually candid docs (tech-debt register & RTM disclose their own defects).

API-001 File download lacks object-level authorization HIGH

PARTIALLY COMPLIANTScore 2Cat 6/7 · Priority P1 · Prod blocker: borderline
Evidence
FilesController.cs:60 Download gated only by class-level [Authorize] + tenant filter; FileReference is ITenantScoped only, not IAllocatable Files/FileReference.cs:12; no documents.view/record entitlement; ids are time-ordered GUIDv7.
Analysis
Any authenticated user within the tenant can retrieve any file by id regardless of access to the owning record or its branch/department. Upload hardening (size, magic-byte sniff, canonical content-type) is otherwise strong.
Risk
Intra-tenant confidentiality breach of regulated evidence (e.g. a technician reading management/HR attachments). Not cross-tenant.
Remediation
Require a module permission and resolve entitlement through the owning aggregate; apply branch/department scope where the parent is IAllocatable.
Required tests
User without documents.view (and out-of-branch) → 403 on GET /api/files/{id}.
Confidence
High.

ESIG-001 E-signature record binding is incomplete; signature ledger not hash-chained HIGH

PARTIALLY COMPLIANTScore 2Cat 15 · Priority P1 · Prod blocker: No
Evidence
ComplianceLedger/LedgerEntries.cs:27-37 binds signer, meaning, SubjectRef, ContentHash, timestamp, tenant — but no structured RecordVersion, Reason, or AuthLevel; version lives only in free-text Meaning (DocumentCommands.cs:156) and SubjectRef=DOC:{id}. Only AuditTrailEntry is hash-chained; the signature ledger is append-only (trigger) but not chained; audit linkage is by string match, not FK.
Analysis
Content modification is detectable (bound SHA-256) and re-signing is required on a new version — the core Part 11 intent is met — but "which version, what reason, what auth assurance, linked to which audit entry" requires parsing free text.
Risk
Weakens 21 CFR Part 11 §11.50/§11.70 signature-to-record binding under scrutiny.
Remediation
Add RecordVersion, Reason, AuthLevel columns; set SubjectRef=DOC:{id}:v{n}; chain/FK-link into the audit trail.
Required tests
Signature captures version+reason; verification detects a version mismatch; chain verify.
Confidence
High.

★Recommended implementation plan

Five workstreams. Phases A–C are the engineering track (sequence them; ~6–7 calendar weeks for a small team). Phase D is the external regulated-validation track and runs in parallel — it, not the code, is the long pole for a compliant go-live. Phase E is maintainability cleanup that can be interleaved. Effort is rough order-of-magnitude for one senior full-stack engineer; each phase ends with an explicit exit gate.

Guiding principle Every fix ships with the test that would have caught it. The codebase already gates behavior in CI (deny-by-default policy, module boundaries, API-surface snapshot) — extend that discipline to each new control rather than relying on review.
