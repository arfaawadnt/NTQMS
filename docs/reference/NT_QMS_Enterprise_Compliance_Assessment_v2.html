6 · Executive summary

NT.QMS is a mature .NET 9 / PostgreSQL 17 / Angular 22 quality-management platform on Clean Architecture with CQRS, serving 20 independent laboratory tenants from one shared application and database. Assessed against the correct control set — with multi-tenancy as a mandatory category rather than an exclusion — it presents as a well-engineered regulated system with a small, specific set of gaps.

Tenant isolation is verified and no cross-tenant exposure exists. This is the finding that matters most, and it was established by attack rather than by inspection. A tenant administrator holding a valid token requested another tenant's document by id and received 404; the same for a file reference. A create request carrying an injected tenantId for a foreign tenant and a chosen id was accepted, and the row landed in the caller's own tenant with a server-generated id — both injected fields ignored. The runtime database role holds neither SUPERUSER nor BYPASSRLS, so the 90 FORCE ROW LEVEL SECURITY policies are enforced by PostgreSQL independently of application code, and 29 tenant-composite foreign keys make a child row under another tenant's parent structurally impossible. Tenant identity is read from the validated JWT's tenant_id claim only — never headers or query strings — and the session GUCs that RLS reads are re-applied on every connection open, so a pooled physical connection cannot carry a previous request's tenant. Per the instruction that any verified cross-tenant exposure is CRITICAL and P0: there is none, and there are zero critical findings.

Regulated-record controls are equally real. Direct UPDATE and DELETE against audit.audit_trail and audit.electronic_signature were both refused by database triggers. The audit ledger is hash-chained: 387 entries, per-tenant sequences, and zero chain breaks under a window-function continuity check. Administrative cross-tenant access is audited — 58 TenantProvisioned entries sit in that ledger, alongside role, permission and user-scope changes. Architectural and authorization rules are enforced mechanically rather than by review: 33 architecture tests hold the dependency direction and module boundaries, and an unannotated command is denied at runtime and fails the build.

What needs work is narrower than the score suggests, and clusters in three places. First, the second, intra-tenant boundary: branch/department scoping is enforced by a single EF query filter with no database backstop, does not cover file attachments, and is dissolved wholesale by eight IgnoreQueryFilters() call sites in the Application layer. Second, three regulated-evidence gaps: the electronic signature binds the signed record's version only inside a free-text sentence, the immutable ledger stores .NET assembly-qualified type names as its event taxonomy, and retention/archival is documented but unenforced with file bytes on mutable local disk. Third, test and contract tails: no unit tests exist for any FluentValidation validator, cross-tenant denial has no automated export or file case, a 429 returns an empty body, and deserialization errors disclose internal type names.

None of these is a cross-tenant or authentication defect. The conditions on approval are proportionate: prove or fix the file-scope gap, correct a token-lifetime configuration drift that contradicts its own ADR, and structure the signature bindings before the next validation cycle.

19 · Observability and operational assessment

Observability. OpenTelemetry traces span HTTP → MediatR → EF/Npgsql → outbox and background jobs, with trace_parent persisted on outbox rows so a single trace survives the asynchronous boundary — a detail frequently missed. Probe and scrape paths are filtered out of traces so monitoring does not pollute the trace store. Production logging is structured JSON with scopes carrying service, environment, tenant, user, correlation id and trace id; OTLP export activates when Otlp:Endpoint is configured. Every response carries X-Correlation-Id (verified) and every problem body carries traceId and correlationId (verified). LoggingBehavior emits request name, tenant, actor, elapsed milliseconds and outcome, and explicitly never payload contents; a repository-wide search found no log site passing a password, secret, token, PIN or connection string, and FieldChangeInterceptor redacts those property names before values reach the ledger. Exceptions are logged once, at the correct boundary. Metrics cover RED, the Npgsql pool and custom business meters, with an alert set documented in deploy/OBSERVABILITY.md.

Two honest deviations. First, the checklist names Serilog; the implementation uses Microsoft.Extensions.Logging with AddJsonConsole. Every structural property the requirement asks for is present, so the intent is met, but the named technology is not used and no ADR records the substitution (DOC-001). Second, /metrics is anonymous and rate-limit-exempt (SEC-001), so the observability surface is the one part of the security posture protected by deployment convention rather than by the application. Trace sampling is unconfigured — all traces export, which is a cost rather than a correctness concern, and it does mean sampling cannot hide failures. Alert and dashboard effectiveness could not be verified without a live environment.

Operations. /health/live is deliberately check-free (Predicate = _ => false) so a database outage recycles traffic rather than the process, and /health/ready is PostgreSQL-backed — both verified 200 with a bare “Healthy” body that discloses nothing, both anonymous and rate-limit-exempt as probes require. Resilience: Npgsql retry with command timeouts; cancellation tokens propagated through 78 Application files; graceful shutdown via stoppingToken with OperationCanceledException handled; advisory-lock leader election so recurring sweeps cannot overlap; outbox claim leases with bounded backoff and dead-lettering; deferred start-up seeding that retries instead of crash-looping when the database is cold, proven by StartupSeedingResilienceTests. No circuit breaker exists, which is defensible with a single database dependency and no outbound HTTP calls, but is not recorded as a decision.

The DatabaseRoleGuard deserves specific credit: Production refuses to start if the connection role is SUPERUSER, holds BYPASSRLS, or owns the tables. It is the deployment gate that makes the tenant-isolation story credible rather than aspirational, and its premise was confirmed here against the live role. The backup/DR runbook is a strong artefact — RPO ≤ 5 min via continuous WAL archiving, RTO ≤ 4 h, retention to a 7-year floor, AES-256 at rest, off-site replication, quarterly drills — but no drill evidence exists, so restore capability is documented, not demonstrated (OPS-001). Given that restore must contend with FORCE-RLS tables and append-only triggers, that untested path carries more risk than the runbook's quality suggests.

22 · Recommended implementation sequence

  1. Answer the one question that changes the work. Is branch/department a security boundary or a relevance filter? It determines whether ACCESS-001 and ACCESS-003 are defects or documentation, and it is answerable in a short conversation.
  2. Write the ACCESS-001 proving test before touching code. A scoped user requesting an out-of-scope attachment either gets 404 or does not. That single test converts the only production blocker into either a closed item or a scoped fix.
  3. Ship the one-line corrections. Jwt:ExpiryMinutes: 15 with a ConfigGuard ceiling (SEC-002), the NC export permission gate (ACCESS-002), and real AllowedHosts (SEC-003). Low risk, immediate benefit, no design work.
  4. Close the two egress test gaps (TEST-002). Cross-tenant export and file tests use fixtures that already exist and protect the paths with the largest blast radius.
  5. Extend the signature ledger (SIG-001) and add the stable event code (AUDIT-002) together — both are additive migrations against append-only tables, so they share a cut-over and should be done before the next validation cycle, since neither can be backfilled.
  6. Close the contract inconsistencies — problem+json on 429 (API-001) and safe deserialization messages (API-002). Small, testable, and they complete a contract that is otherwise uniform.
  7. Make the weaker boundary mechanical. The IgnoreQueryFilters allow-list test (ACCESS-003) and the scope-denial matrix (TEST-003) convert resource scope from convention into a build-breaking rule — the same treatment tenancy already receives, and the reason tenancy is verifiable today.
  8. Add validator tests (TEST-001), starting with StrongPassword and every MaximumLength that is the only length control for a text column.
  9. Record elevation (SEC-004) — eight call sites, one security event each.
  10. Add RLS to user_account (DB-001), verifying the pre-tenant login path against the new policy.
  11. Secure /metrics (SEC-001) so the control lives in the application rather than in proxy configuration.
  12. Run the restore drill (OPS-001). It needs an environment, not a code change, and it is the largest untested control in the system.
  13. Address retention and storage (DB-002) — the biggest item, and the one most needing an explicit decision before code.
  14. Expose the concurrency token (API-003) across API and SPA together, then present conflicts in the UI (UI-001).
  15. Introduce the first value objects (DOMAIN-001) on new code and the four highest-risk concepts; do not retrofit wholesale. Finish with documentation (DOC-001) and container hygiene (OPS-002).
