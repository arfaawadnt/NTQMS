NT.QMS — Enterprise Architecture Remediation Plan

An ordered, gated implementation plan to close the findings of the Enterprise Architecture Compliance Audit (EA-AUD-NTQMS-001) and lift NT.QMS from "approved with conditions" to an unconditional production posture — structured on the AWS Well-Architected pillars and delivered as a continuation of the existing v1.25→v1.37 release train.

Guiding principles

  • Gated release train. Each phase ships as a tagged increment behind the existing CI gate (build + ~310 tests + real-PostgreSQL integration + architecture boundaries). No phase merges until its acceptance tests are green.
  • No regression of the strong core. The verified controls — tenant isolation, backend authorization, audit/immutability, e-signature — are load-bearing; every change adds an accompanying test and must keep the existing suite green.
  • Well-Architected alignment. Work is grouped by the pillar it most serves: Reliability, Operational Excellence, Security, Performance Efficiency, Cost Optimization.
  • Safety-first ordering. Cheap, high-safety deployment gates first; then data-consistency and messaging robustness; then observability; then edge hardening and polish — mirroring the mandated remediation-priority order.
  • Every change is provable. Each finding has explicit acceptance criteria and the test that proves it; documentation-only decisions are captured as ADRs.

02 Well-Architected pillar mapping

Reliability

Optimistic concurrency (DB-009), Outbox dead-letter/backoff/dedup/retention (MSG-004…007), readiness health (OPS-008), scale-out safety (OPS-002), DB retry/circuit-breaker (OPS-009), CHECK constraints (DB-005).

Operational Excellence

Structured log sink (OBS-001), distributed tracing + correlation IDs (OBS-002/API-006), metrics/alerts/dashboards (OBS-003), ADR record set (ARCH-006), test-coverage gaps (TEST-*).

Security

Least-privilege role gate (TENANT-004), rate limiting (SEC-013), security headers/CSP (SEC-011), TLS/HSTS confirmation (SEC-012), token-storage decision (SEC-017), study-DELETE authz + authorization behavior (SEC-003/CQRS-003).

Performance Efficiency

Real pagination vs silent cap (API-004), query-plan review & indexes (DB-010 follow-up), connection-pool/retry tuning (OPS-009), OTel-driven latency baselines (OBS-002).

Cost Optimization

Outbox retention purge to bound storage (MSG-007), container resource limits (DEPLOY-003), telemetry sampling that never hides failures (OBS-003).

03 Phase detail

Phase 0 — Deployment safety gatesv1.38.0 · P0 · S

Cheapest, highest-safety work; clears the two hard blockers that gate any production release and the operational gate on which tenant isolation depends.

Tasks

  • TENANT-004 — Add a startup guard that refuses to boot in Production if the DB connection role has BYPASSRLS or is the table owner; document/automate applying deploy/harden-runtime-role.sql; add a CI check that the RLS integration tests run as qams_app.
  • OPS-008 — Register a DB-backed readiness check (AddHealthChecks().AddNpgSql()/AddDbContextCheck() tagged ready); expose /health/live (self) and /health/ready (DB + critical deps); repoint the Dockerfile HEALTHCHECK and any LB/orchestrator probe at /health/ready.
  • OPS-002 — Decision + implementation: for the near term, enforce and document single-replica (deployment manifest replicas: 1 + a startup log warning if a peer lock is contended); schedule the durable fix in Phase 1 (Outbox SKIP LOCKED claim + advisory-lock/leader election for sweeps).
Acceptance: app refuses to start as an over-privileged role; /health/ready returns Unhealthy when PostgreSQL is stopped and Healthy when up; a documented topology exists (single-replica or the Phase-1 scale-out control). Tests: readiness-fails-when-DB-down integration test; boot-as-owner rejected test.

Dependencies

None. Ship first.

Phase 1 — Data consistency & messaging robustnessv1.39.0 · P1 · M–L

Tasks

  • DB-009 / VAL-003 — Add PostgreSQL xmin as a concurrency token on mutable aggregate roots (modelBuilder.Entity<T>().UseXminAsConcurrencyToken() — no schema change), or a RowVersion on AggregateRoot; map DbUpdateConcurrencyException → HTTP 409 with a stable code in DomainExceptionHandler.
  • MSG-004 — Add an outbox_dead_letter table (or a dead_lettered_at flag); move rows past MaxAttempts there; isolate per-event so one poison event cannot head-of-line-block the batch; emit a metric/alert.
  • MSG-005 — Per-event exponential backoff via a next_attempt_at_utc column with jitter; the processor selects only rows due for retry.
  • MSG-006 — A processed-event inbox keyed on (EventId, handler), or assert idempotency in each policy via a natural unique key (e.g. NC-per-source); redelivery must net a single side-effect.
  • MSG-007 — Implement the documented Outbox retention purge (delete processed_at_utc < now − retention) as a scheduled sweep, or correct the stale comments.
  • OPS-002 (durable) — Outbox claim with FOR UPDATE SKIP LOCKED + a lease; advisory-lock/leader election for the recurring sweeps, enabling safe horizontal scale-out.
Acceptance: two concurrent transitions on one aggregate → exactly one succeeds (other 409); a permanently-failing event lands in dead-letter after N attempts without blocking a healthy following event; crash-between-publish-and-commit yields one net side-effect; two processors publish each row once; processed rows are purged on schedule. Tests: concurrency-conflict, poison→dead-letter (no HOL block), redelivery-idempotency, two-processor exactly-once, retention purge.

Dependencies

Phase 0 topology decision informs the SKIP-LOCKED/leader-election work.

Phase 2 — Observability baselinev1.40.0 · P1 · L

Tasks

  • OBS-001 — Structured JSON logging with a real sink (Serilog or the built-in JSON console formatter → OTLP/Seq/Elastic/Loki) with retention aligned to the DR runbook; standard enriched properties (service, environment, tenant, user, operation, outcome, duration).
  • OBS-002 / API-006 — Add OpenTelemetry tracing (ASP.NET Core + Npgsql + a MediatR pipeline span + background-job spans) with OTLP export; generate/propagate a correlation ID via middleware, enrich logs with trace/span/correlation IDs, and return it safely in responses and ProblemDetails traceId.
  • OBS-003 — Emit metrics (System.Diagnostics.Metrics): RED (request rate/errors/latency), DB pool, Outbox backlog age + dead-letter count, sweep liveness; publish a metrics endpoint; define actionable alerts (error-rate, p95 latency, Outbox backlog/age, sweep-hasn't-run, dead-letter>0).
Acceptance: a single request produces correlated logs + a trace spanning HTTP→MediatR→EF→Outbox with a shared trace id returned to the client; the Outbox dead-letter condition (from Phase 1) raises an alert; log shape asserted by test. Tests: JSON log-shape/required-fields test; trace-context-propagation test across the async job boundary.

Dependencies

Best after Phase 1 so the new dead-letter/backoff metrics have something to emit.

Phase 3 — Edge & security hardeningv1.41.0 · P1/P2 · M

Tasks

  • SEC-013 / API-002 — AddRateLimiter/UseRateLimiter with a global window plus stricter partitions on /api/auth/* and the password+PIN publish/e-signature endpoints; return 429; (or document + configure the reverse-proxy equivalent).
  • SEC-011 — Security-headers middleware: HSTS, a locked-down Content-Security-Policy, X-Content-Type-Options:nosniff, X-Frame-Options:DENY/frame-ancestors 'none', Referrer-Policy:no-referrer.
  • SEC-012 — Confirm the reverse proxy enforces TLS + HSTS, or add UseHttpsRedirection+UseHsts in-app; record the decision.
  • SEC-017 — Decide token storage: move the access token to memory + an httpOnly SameSite refresh cookie, or (if localStorage stays) ship the strict CSP from SEC-011 and shorten token lifetime — capture the risk-acceptance ADR.
Acceptance: burst of login attempts → 429; security headers present on every response and a CSP that blocks inline script; TLS/HSTS demonstrably enforced. Tests: rate-limit 429 functional test; response-headers assertion test.

Dependencies

Independent; can run in parallel with Phase 2.

Phase 4 — API & application-pipeline polishv1.42.0 · P2 · L

Tasks

  • API-003 — Emit application/problem+json and route the auth/tenant/change-reason middleware errors through the same ProblemDetails writer (kill the anonymous-object shape drift); ensure the concurrency 409 (Phase 1) is uniform.
  • API-004 — Replace the silent .Take(500) caps with a real pagination envelope (page/size or cursor + total/hasMore); allow-list any client sort.
  • API-005 — File hardening: content-type/extension allow-list + magic-byte sniffing on upload; force Content-Disposition: attachment (or serve from an isolated origin) on download.
  • CQRS-003/004 — Add an AuthorizationBehavior (policy marker per request) + an IdempotencyBehavior for unsafe retryable commands; role-gate the currently-ungated commands (e.g. NC Raise/Submit, analytical add/calculate/DELETE).
  • API-001 — Introduce Asp.Versioning.Mvc with api/v1/... and a documented contract-evolution policy.
Acceptance: all errors are problem+json with stable code; list endpoints page correctly with a total; disallowed uploads rejected and downloads forced to attachment; a command without its policy is denied by the behavior; versioned routes resolve. Tests: ProblemDetails contract test, pagination boundary/navigation test, file type + disposition test, authorization-behavior deny test, version-routing test.
Phase 5 — DB integrity, configuration & containerv1.43.0 · P2 · M

Tasks

  • DB-005 — Add CHECK constraints for enum domains (or PG enum types), non-negative monetary/quantity columns, and date-ordering invariants on regulated tables — the DB as last line of defense.
  • CFG-001/002 — Move options to services.Configure<T>().ValidateDataAnnotations().ValidateOnStart(); validate the connection string and all security options at startup so a mistyped MFA/policy value fails fast instead of silently defaulting.
  • OPS-009 — Enable Npgsql EnableRetryOnFailure + a command timeout; consider a resilience pipeline for SMTP.
  • DEPLOY-002/003 — Run the container as non-root (USER app), add CPU/memory limits, and publish a production orchestration manifest (pinning replicas per the Phase-0/1 decision).
Acceptance: invalid enum/negative value rejected by PostgreSQL; boot with blank/invalid critical config fails fast; container runs as non-root with resource limits. Tests: constraint-rejection migration test; invalid-config fast-fail test.
Phase 6 — Test coverage & governancev1.44.0 · P2/P3 · M–L

Tasks

  • TEST-001/002/003 — ProblemDetails contract tests; optimistic-concurrency conflict test; Outbox processor retry/dead-letter test; inbox/dedup test; migration up/down round-trip smoke test; mid-chain audit-tamper detection test; a baseline load/perf suite.
  • ARCH-004 — NetArchTest fact forbidding cross-module type references (enforce the modular-monolith boundary). ARCH-005 — OpenAPI/contract snapshot diff test. ARCH-006 — stand up docs/adr/ (MADR) with the records listed in §04.

04 Required ADRs (decisions to formalize)

  • Optimistic concurrency strategy (xmin token) alongside the existing trigger-based immutability.
  • Outbox reliability model: dead-letter + backoff + dedup, and the horizontal-scale claim mechanism (SKIP LOCKED/leader election).
  • Deployment topology & the single-replica → scale-out transition.
  • Token-storage decision (localStorage risk-acceptance vs httpOnly cookie).
  • Same-origin deployment assumption (no CORS by design) and the API-versioning/contract-evolution policy.
  • Application coupling to EF Core DbSet in the persistence port (accepted Clean-Architecture convention).

05 Sequencing, critical path & effort

Critical path to unconditional release

  1. Phase 0 (2–4 d) — safety gates, ship immediately.
  2. Phase 1 (~2 wk) — concurrency + Outbox robustness (the two P1 blockers).
  3. Phase 2 (~1.5–2 wk) — observability, so production is diagnosable.
  4. Phase 3 (~1 wk, parallelizable with P2) — rate limiting + headers/CSP.

≈ 5–6 weeks of focused effort clears every production blocker and the highest-risk gaps.

Parallelization

Phase 3 (security edge) is independent of Phases 1–2 and can run concurrently with a second engineer. Phase 5 (config/container/CHECK) and Phase 6 (tests/ADRs) can begin opportunistically once their target areas stabilize.

Capacity note: effort is indicative for one senior engineer excluding review and any CSV re-validation; calendar time depends on team size and the QA/validation bandwidth (the long pole for a regulated system).

Definition of Done (per finding)

Code merged behind the CI gate · accompanying automated test green · no regression in the ~310-test suite · migration (if any) applied to a real PostgreSQL · documentation/ADR updated · finding re-verified closed with file:line evidence.

06 Risk if deferred & explicit non-goals

If deferred…Consequence
Phase 0 (readiness / role gate)Traffic routed to broken instances; worst case, RLS silently bypassed if prod runs as owner — a tenant-isolation defeat.
Phase 1 (concurrency / Outbox)Silent lost-updates on regulated records and silently-stranded integration events (finding→NC etc. never fire) — data-integrity erosion invisible to operators.
Phase 2 (observability)Production incidents are near-undiagnosable; MTTR unbounded; no early warning on Outbox backlog or sweep failure.
Phase 3 (rate limit / headers)Brute-force exposure on auth & e-signature; a single XSS exfiltrates the localStorage token absent a CSP.
Explicit non-goals for this plan: no domain/feature redesign, no re-architecture off the modular monolith, no migration away from EF Core — the strong, verified core is preserved. SignalR/real-time remains out of scope (no requirement). Formal CSV re-validation of the changed areas (updating the IQ/OQ/PQ & RTM) is a downstream activity, not part of this engineering plan.
