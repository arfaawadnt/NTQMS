What this report is. A single consolidated view over four registers that previously had to be read together: the CSV/Part-11 validation set (docs/validation/), the enterprise application audit (EAC-NTQMS-001 rev 4), the schema-hardening programme (SCHEMA-HARDENING-REPORT.md), and the engineering log. Every figure was read from the live catalogue, a test run, or a named document — none is carried forward from a previous revision without re-checking.

1. Position in one paragraph

NT.QMS is feature-complete and defect-free against every check that can be run without a deployed, qualified environment. All 18 original CSV/regulatory findings are closed; the enterprise-architecture remediation train is complete; and the two programmes since the last report — configurable authorization (v1.51.0/.1) and database schema hardening (v1.51.2) — are shipped, verified by catalogue introspection and exercised live. What is not done is external and environmental: an independent penetration test, formal validation execution with signatures on a qualified installation, and a staging bring-up with observability and load. Those three have been the outstanding items since v1.41 and none of this cycle's work advances them.

3. Defects raised and closed this cycle

Read this section before the scores. Four defects were found in this cycle. Three of them escaped a green test suite and were caught only by driving the running application by hand. That is the single most important quality signal in this report — and it is why the fourth item, VER-001, was raised against the verification strategy itself rather than against any feature.

4. Tenant isolation — the control that changed most

Revisions 1–3 of the architecture audit scored multi-tenancy 4/4 on the strength of "EF query filter + PostgreSQL FORCE RLS". That was true of aggregate roots and not true of the 30 owned child tables (rca_record, capa_action, document_version, role_permission and the rest), which carried no tenant column at all — a direct SELECT returned every tenant's rows. The audit's verification method was the weakness: it accepted "RLS is on" without asking on which tables.

8. Honest limitations of this report

  • All execution evidence is from a development workstation. Nothing in this cycle ran on a qualified or staging installation. CI does run every migration against a clean PostgreSQL, which is stronger than a developer machine but is still not a qualified environment.
  • The one witnessed OQ is unsigned. Doc 12 is an execution transcript: the results are real, the attestation is pending. The v1.51.2 cases have no witnessed session at all.
  • Independence is limited. The party that wrote the code also wrote and executed the checks. An external assessor will note the absence of segregation of duties.
  • The architecture score is self-assessed against a checklist, not certified by a third party.

9. Recommendation

Approved with conditions, unchanged in substance from rev 2 — the conditions are the same three, and they are the same three that have been open since v1.41. What changed is the confidence behind the approval: a material isolation gap that previous revisions scored as passing has been found and closed, and the verification weakness that allowed three defects to escape has itself been closed. Production use should remain gated on SEC-001, DOC-001 and OPS-001.
