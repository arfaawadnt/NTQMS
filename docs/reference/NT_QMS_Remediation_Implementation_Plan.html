01

Governing Principles

The plan is engineered to three overlapping rulebooks simultaneously — the regulatory lifecycle (GAMP 5), the AWS-style Well-Architected pillars, and preservation of the existing clean/DDD architecture. Nothing in the remediation is a bolt-on that undermines these.

Security

Least-privilege DB roles, enforced MFA, active RLS, segregation of duties — defence in depth, not single-layer.

Reliability

Backup/restore & DR proven; append-only ledgers; deterministic, replayable outbox.

Operational Excellence

Formal change control, release authorization, CI evidence, monitored deployments.

Data Integrity

ALCOA+ enforced at the database, not only in code; reason-for-change on every regulated edit.

Validation (GAMP 5)

Risk-based V-model: URS→FS/DS→config, IQ/OQ/PQ traced by an RTM to executed evidence.

Architecture-preservation rule. Remediations are implemented at the correct layer: cross-cutting controls via EF interceptors & migrations (isolation, immutability, stamping), business rules via domain guards (SoD, reason-for-change, effective-dating), integrations via Application ports. No compliance logic is scattered into controllers or the UI; the single centralized services (identity, e-signature, audit, notifications) remain the only implementations.
02

Remediation Strategy

Work is grouped into six workstreams and sequenced by risk and dependency, not by convenience. The two data-layer blockers (F-01, F-02) come first because every later control assumes the database itself is trustworthy. CSV execution (WS4) runs partly in parallel — its documentation set is authored alongside the fixes it will later qualify — but its IQ/OQ/PQ execution is gated behind a frozen, fix-complete build.

WS1

Tenant Isolation & Database Hardening

WS1

Make the database itself the last line of defence

F-01F-02F-12
Objective

Move tenant isolation and regulated-record protection from application-only controls to enforced, defence-in-depth database controls, so no bug, admin, or raw-SQL path can cross tenants or silently alter a signed record.

Technical approach (architecture-respecting)
  1. Split the DB roles. Migrations run as qams_owner; the runtime connection uses a new non-owner, least-privilege role qams_app. Owners bypass RLS — the runtime must not own tables.
  2. Force RLS. Add ALTER TABLE … FORCE ROW LEVEL SECURITY to every tenant-scoped table (new migration, generated from the ITenantScoped set so coverage can't drift).
  3. Set the tenant GUC per unit of work. Add a DbConnectionInterceptor that issues SET LOCAL app.current_tenant = <jwt tenant> on each connection/transaction, sourced only from the validated JWT claim (never headers). Provide a single audited elevation path for platform-admin/background jobs instead of ad-hoc IgnoreQueryFilters().
  4. Codify least-privilege grants. Migration grants runtime role SELECT/INSERT/UPDATE on business tables, SELECT/INSERT only on audit.*, and no DELETE on regulated tables.
  5. DB-level immutability. Add a trigger that rejects UPDATE/DELETE on rows in a signed/closed state (keyed on the state column), extending the append-only pattern already used on audit.* to signed qams.* records — defence-in-depth behind the domain guards (F-12 resolves as a consequence).
Acceptance criteria / evidence
  • Integration test: a request authenticated as Tenant A cannot read or write Tenant B rows via any path, including event-policy queries — proven against real PostgreSQL.
  • Integration test: UPDATE/DELETE of a signed-off study/document is rejected at the database.
  • Runtime role verified as non-owner with no DELETE on regulated tables (grant inspection captured as IQ evidence).
WS2

Data Integrity & Records

WS2

Complete ALCOA+ for every regulated change

F-06F-08F-13F-14
Technical approach
  1. Reason-for-change (F-06). Thread a mandatory reason through every mutating command on regulated aggregates (evidence void/removal, target changes). Persist it on the FieldChangeRecord (add a Reason column + capture in the interceptor) so the audit trail answers "why", not just "what".
  2. Effective-dated QC targets (F-06). Replace QcProfile.UpdateTargets in-place overwrite with a new versioned, forward-only target row; historical QC verdicts keep referencing the target in force at run time.
  3. Failed-signature logging (F-08). Inject the security-event log into ESignatureService; record every failed component check and add throttling/lockout mirroring the login path.
  4. Archive integrity (F-14). Make the content snapshot mandatory on ArchiveEntry.Archive; add a LegalHold state that blocks disposal regardless of retention expiry.
  5. Inspector export (F-13). Add a read-only endpoint exporting the audit trail + signature manifest to a human-readable file (CSV/PDF) for inspections.
Acceptance criteria / evidence
  • Attempting a regulated edit/void without a reason is rejected; the reason appears in the trail export.
  • Changing a QC target creates a new effective-dated record; prior verdicts are unchanged.
  • Failed e-signature attempts appear in the security-event ledger and trigger throttling.
WS3

Access Control & Part 11 Signatures

WS3

Enforce the controls that already exist

F-04F-05F-07F-15
Technical approach
  1. Enforce MFA (F-04). Add a policy requiring TOTP enrollment for TenantAdmin/PlatformAdmin (configurable per tenant); block privileged actions until enrolled. TOTP already exists — this is enforcement, not new crypto.
  2. Segregation of duties (F-05). Add author≠signer guards in ValidationStudy, UncertaintyBudget, PtPlan sign-offs and NC verify, mirroring the proven ControlledDocument/CAPA-close pattern (SOD-* domain errors).
  3. Session lifecycle (F-07). Introduce short-lived access tokens + refresh tokens with server-side revocation (token version / IsActive re-check), so deactivation or role change takes effect immediately and idle sessions expire.
  4. Password policy (F-15). Unify minimum length at ≥12 across all paths; add complexity and breached-password screening (k-anonymity / local list).
Acceptance criteria / evidence
  • A privileged user without MFA is blocked; a deactivated user's token is rejected on the next request.
  • The same user cannot both create and sign off any regulated record (negative test per aggregate).
WS4

Computerized System Validation (GAMP 5)

WS4

Build the validated-state evidence — the long pole

F-03F-09F-10
Approach — risk-based V-model
  1. Plan & classify. GAMP 5 software-category assessment (this is a configured/custom application → Category 5 elements); author & approve the Validation Master Plan.
  2. Specify. Retro-derive an approved URS from the SOW + delivered behaviour; author the Functional/Design Specification and Configuration Specification from the existing architecture documents (elevate them from engineering notes to controlled specs).
  3. Assess risk. Function-level risk assessment (FMEA) prioritising GxP-critical functions (e-records, signatures, isolation, result-affecting calculations).
  4. Trace. Build the Requirements Traceability Matrix: URS → FS → risk → test (IQ/OQ/PQ) → evidence.
  5. Qualify. Execute IQ (install/config on the qualified target platform, incl. DB-role & grant verification from WS1), OQ (functional test protocols — largely automated by WS6's real-PostgreSQL suite as attached evidence), and PQ/UAT (business-process scenarios run by lab users).
  6. Conclude. Approve the Validation Summary Report and a formal release authorization.
Continuous evidence (F-09) & resilience (F-10)
  • WS6 CI runs the regulated-behaviour test suite against real PostgreSQL on every change — these executed results become reusable OQ evidence under change control.
  • Execute and document a backup/restore drill and a DR test with defined RTO/RPO; attach as PQ/operational evidence.
Sequencing note. WS4 documentation is authored in parallel from Phase 0; WS4 execution (IQ/OQ/PQ) only starts once the build is frozen at end of Phase 2 — validating a moving target wastes the evidence.

Governance & Configuration Control

WS5

Close the QMS-completeness & configuration gaps

F-11F-16F-17F-18
New / extended modules (F-11) — reuse existing patterns
  • Quality policy aggregate (versioned, approved, communicated) — reuses the controlled-document lifecycle.
  • Read-and-understand acknowledgement — a per-document receipt linked to training/competency; SOP revision triggers a training-impact reassignment.

  • Secrets hygiene (F-17): move dev credentials to user-secrets/secret store; rotate; keep production settings secret-free (already the case).
  • Frontend/e2e coverage (F-18): component + end-to-end tests for regulated workflows (sign-off, approvals, tenant switching).

Test Automation & Operational Readiness

WS6

Prove it, on the real platform, every time

F-09F-10F-18
Technical approach
  1. Real-database integration harness. Replace the EF In-Memory swap in the functional test factory with Testcontainers PostgreSQL, so RLS, grants, triggers, delete/restrict semantics and migrations are exercised exactly as in production.
  2. Regulated-behaviour test pack. Cross-tenant denial, post-sign-off immutability, e-signature dual-component + failure logging, audit-chain tamper detection, authorization matrix (positive & negative per role) — this pack doubles as reusable OQ evidence.
  3. CI/CD gates. Block merge/release on test failure; capture signed, timestamped test artifacts for the validation file.
  4. Operational runbooks. Backup/restore, DR failover, key rotation, tenant provisioning — documented and drill-tested.

06

Engineering Guardrails (well-architected)

Do

  • Implement cross-cutting controls in interceptors & migrations; business rules in domain aggregates; integrations behind Application ports.
  • Generate RLS/immutability migrations from the ITenantScoped/state model so coverage cannot drift.
  • Keep every regulated write inside a transaction that also writes its ledger entry.
  • Make new controls testable and add them to the real-PostgreSQL CI pack as you go.
  • Version and change-control any configuration that affects a result or a control.

Don't

  • Don't place compliance logic in controllers or the UI.
  • Don't add new IgnoreQueryFilters() paths without a reviewed, audited elevation reason.
  • Don't overwrite regulated values in place — void-and-re-enter or effective-date.
  • Don't run the runtime app as the table-owning DB role.
  • Don't start IQ/OQ/PQ against an unfrozen build.

Go-Live Gate — Definition of Done

Controlled production go-live is authorized only when all of the following are evidenced.
  1. Cross-tenant isolation enforced at the database and proven by automated test on real PostgreSQL (F-01).
  2. Signed/closed regulated records cannot be updated or deleted except through controlled workflow; runtime DB role is least-privilege (F-02).
  3. Approved GAMP 5 validation package with executed IQ/OQ/PQ traced by the RTM and an approved Validation Summary Report (F-03).
  4. MFA enforced for privileged roles; segregation of duties on every sign-off; reason-for-change on all regulated edits (F-04, F-05, F-06).
  5. Session revocation active; failed-signature logging in place (F-07, F-08).
  6. Backup/restore and DR tested with documented RTO/RPO (F-10).
  7. Priority governance gaps closed (quality policy, read-&-understand, legal hold, PIR) (F-11).
  8. Formal change control & release-authorization SOPs operating.

On completion, the audit recommendation moves from Production release prohibited to Approved with documented conditions for a monitored rollout.
