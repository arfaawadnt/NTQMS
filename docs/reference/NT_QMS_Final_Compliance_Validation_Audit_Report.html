01 Executive summary

What was found, what was done, and what remains.

The initial CSV & Regulatory Readiness Audit determined that NT.QMS had a strong functional footprint but carried three go-live blockers — dormant tenant isolation, mutable signed records, and an absent validation documentation set — alongside gaps in Part 11 access controls, data-integrity provenance, and lab-governance capabilities. A structured remediation program addressed the findings in gated releases, each shipped with tests and verified against a real PostgreSQL instance. This report records an independent re-verification: the controls now exist in code, are wired into the request/persistence pipeline and the database, and are exercised by an automated suite that runs in CI against real PostgreSQL. The remaining work is not development — it is the formal, signed execution of the now-complete IQ/OQ/PQ protocols plus the operational items in §7.

04 Independent re-validation methodology

Verification was performed by three independent, read-only re-audits plus the automated evidence base — deliberately separated so no single perspective could self-confirm.

Re-audit A — Part 11 & data integrity

F-02, F-05, F-06, F-07, F-08, F-13, F-15 + the hash-chained audit trail and field-change ledger. 11/11 closed. Skeptical probes confirmed the SoD check and the reason-for-change flow are not silent no-ops.

Re-audit B — tenancy, security & infra

F-01, F-04, F-09, F-10, F-16, F-17. 6/6 closed. Confirmed every tenant table forces RLS in its own migration and zero literal role strings remain in controllers.

Re-audit C — governance, records & frontend

F-11 (all six sub-features), F-12, F-14, F-18. 4/4 closed. Each control verified across domain + API + persistence; domain layer scanned clean of stubs/fakes.

Automated evidence base. ~270 backend tests (5 projects, incl. real-PostgreSQL integration & architecture-boundary gates), 37 frontend unit tests, and a Playwright e2e suite — all green, all run in CI on every push against a provisioned non-superuser PostgreSQL 17.

05 Data-integrity & Part 11 control map

The load-bearing GxP controls and where they live.

  • Tamper-evident audit trail — per-tenant SHA-256 hash chain (EntryHash = SHA256(PrevHash‖Seq‖EventId‖EventType‖Payload‖OccurredAt)) with on-demand chain verification; a break is detectable and surfaced in exports.
  • Field-level provenance (ALCOA+) — contemporaneous old→new capture in the same transaction, credential values redacted, now carrying the operator's reason-for-change.
  • Immutable signed records — database trigger rejects mutation of signed/approved rows; defence-in-depth via a no-DELETE runtime role.
  • Dual-component e-signatures — password + PIN re-authentication, meaning + content hash bound to the signed record; failures logged and locked out.
  • Segregation of duties — author ≠ reviewer ≠ approver enforced in the domain for NC/CAPA, all analytical sign-offs, and quality-policy approval.
  • Tenant isolation — two independent layers (EF filter + forced PostgreSQL RLS), fail-closed, verified against a real database.

08 Residual observations (non-blocking)

Legacy segregation-of-duties. The author≠signer guard on analytical sign-off is intentionally skipped for records created before the preparer id was captured (or by system processes). This is a documented, bounded design decision — not a regression — and applies only to pre-remediation data.
Operationally-verified controls. Backup/DR (RPO/RTO) and the client idle-session timeout are configuration/operational controls confirmed at IQ / by restore drill and at OQ respectively, rather than by automated test — expected for these control types and captured in the RTM.
