NT.QMS — Automated Adversarial Security Assessment

An executed, black/grey-box security probe of the running NT.QMS API, exercising the attack classes the system is designed to defend (OWASP API Security Top-10 aligned). Fifteen adversarial checks were fired at a live instance and their defences verified.

Scope & honesty statement — read first. This is an automated assessment against a local development instance, executed by the engineering harness (scripts/security-probe.ps1). It is NOT a penetration test against a staging deployment, and it does not discharge that external activity. No staging environment exists yet (closure-report residual R-7), and a defensible penetration-test attestation for a 21 CFR Part 11 system must be performed by a qualified independent party against a production-like deployment. This report’s purpose is to de-risk and pre-empt that engagement by proving the in-code defences hold under real attack traffic. The authoritative pen test remains OPEN (see §D).

B · Method & artefacts

  • Harness: scripts/security-probe.ps1 — re-runnable, prints PASS/FAIL per check, exits non-zero on any failure (suitable as a pre-release gate against a deployed URL).
  • Target: the running API at v1.48.0 against a real PostgreSQL 17 with FORCE RLS and the hardened runtime role, i.e. the real data-layer defences are in the loop — not mocked.
  • Corroborating deterministic tests (the assessment confirms live what these prove in CI): RlsTenantIsolationTests (tenant isolation / fail-closed), RoleEndpointMatrixTests (6-role × endpoint deny matrix), SignedRecordImmutabilityTests, ProblemContractTests, SecurityHardeningTests (headers + 429), FileHardeningTests (upload sniffing).

C · Assessment notes (not findings)

  • HSTS is intentionally absent in the Development environment and emitted only outside it (ADR-0002); verify its presence on the TLS-terminated staging/production host.
  • The probe's ordering matters: the credential-burst check (E1) exhausts the per-IP auth rate-limit budget, so it runs LAST — an earlier version mis-flagged the subsequent auth-shape checks; corrected and re-verified.
  • The BOLA check (C1) creates one draft nonconformance in the dev tenant (regulated records are never hard-deleted); harmless on a dev instance, but run destructive-write probes against disposable data only.
