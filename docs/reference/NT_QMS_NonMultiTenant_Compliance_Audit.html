1 · Objective and reviewed scope

Determine how closely NT.QMS complies with the supplied Enterprise Application Architecture instructions, using concrete evidence from source, database, configuration, deployment and test artefacts — not from folder names, package references or intended architecture.

Scope covered: solution and project structure; domain model; application use cases; API surface; authentication and authorization; resource-level and organizational data access; EF Core mappings and PostgreSQL schema; transactions and the outbox; background jobs; the Angular client; validation and error contracts; audit trail and electronic signatures; security architecture (STRIDE); logging and observability; configuration and secrets; health, resilience and operations; container and deployment manifests; the automated test suite; and documentation traceability.

2 · Application and deployment classification

The declared classification does not hold. The brief classifies this application as NON-MULTI-TENANT and instructs that tenant identifiers, tenant-scoped queries, PostgreSQL tenant RLS, tenant-aware jobs and cross-tenant isolation controls must not be required. NT.QMS is a deliberately, comprehensively multi-tenant SaaS platform. Measured evidence:

  • saas.tenant is a first-class registry table holding 20 active tenants in the inspected database, each an independent laboratory (demo-lab, arfa, iso-test-2, …).
  • 45 domain types implement ITenantScoped (src/NT.QAMS.SharedKernel/MultiTenancy/ITenantScoped.cs).
  • 90 tables carry FORCE ROW LEVEL SECURITY with a tenant_isolation policy; 88 tables use a tenant-first composite primary key (tenant_id, id); 29 of 36 foreign keys are tenant-composite.
  • The JWT carries a tenant_id claim, resolved by TenantResolutionMiddleware and pushed into the PostgreSQL session GUC app.current_tenant on every connection open (TenantConnectionInterceptor).
  • One organization does not own the deployment: a platform control plane (ProvisionTenantCommand, PlatformControllers, UserRole.PlatformAdmin) exists specifically to onboard further independent customers into the same application and database.

Per the brief’s own instruction, this is recorded as a critical architecture concern (CLASS-001) and a dedicated multi-tenancy assessment is recommended. The audit was not narrowed: tenant isolation was assessed and tested as the primary data-isolation boundary, and the intra-tenant organizational boundary (branch / department) was assessed under §9.

7 · Executive summary

NT.QMS is a mature, unusually well-disciplined .NET 9 / PostgreSQL 17 / Angular 22 quality-management platform built on Clean Architecture with CQRS. Its architectural boundaries are not aspirational — they are enforced by 33 passing architecture tests, a command-authorization CI gate, module-boundary and API-surface snapshot gates. Its regulated-record controls are not claimed — they are enforced in the database by FORCE ROW LEVEL SECURITY, append-only triggers and a hash-chained audit ledger, all of which this assessment attacked directly and could not break.

The single largest issue is not a defect in the software: the application was submitted for the wrong assessment. It is a multi-tenant SaaS platform serving 20 independent laboratories from one shared application and database. The brief instructed that tenant isolation controls not be required; had that instruction been followed literally, the most consequential control surface in the system would have gone unexamined. It was examined instead, and it held: a tenant administrator presenting a valid token for another tenant’s document id received 404, not the document.

What genuinely needs work clusters in one place: the second, intra-tenant boundary. Branch and department scoping is enforced by a single EF global query filter plus a write-side interceptor — with no database-level backstop, no coverage of file attachments, an export endpoint that skips the permission gate its siblings carry, and eight IgnoreQueryFilters() call sites in the Application layer that dissolve the filter entirely. Tenant isolation is defended in depth; organizational isolation is defended once. Beyond that, the remaining findings are the ordinary tail of a system at this maturity: a shipped token lifetime that contradicts its own ADR, a 429 with no problem+json body, internal type names in a deserialization error, an electronic-signature record that binds the signed record’s version only inside a free-text string, and a domain that has exactly one value object across 45 aggregates.

Nothing found is exploitable across the customer boundary. The conditions on approval are: prove or fix the file-scope gap, correct the token-lifetime drift, structure the signature bindings, and re-run this assessment under the multi-tenant control set that actually governs the system.

Observed implementation
Cross-tenant file access is correctly blocked — a demo-lab token requesting an arfa-owned file_reference id returned 404 at runtime. Within a tenant, however, FileReference falls on the non-allocatable side of the query filter, so no branch or department term is applied and the download resolves on id alone. Attachments belonging to department-restricted records (complaints, nonconformances, audits — all IAllocatable) are therefore reachable by any authenticated tenant member.
Compliance analysis
The parent record is scope-protected; its evidence file is not. Because the scope filter is what makes the parent unreadable, the file is the one path that reaches the same regulated content without passing the same check. A brute-force attempt is not required — file ids surface in URLs, exports and version histories.
Risk
Intra-tenant confidentiality breach of regulated evidence. Concretely: Complaint masks the reporter’s identity for roles lacking the confidential-view privilege (ComplaintCommands.cs:200-206), yet an attachment naming that reporter is downloadable by any authenticated user in the tenant. That defeats a control the domain deliberately implements.
Required remediation
Preferred: authorize the download against the owning record — resolve the file through its parent aggregate so the existing scope filter applies, or add an explicit scope check on the link table. Alternative, if lab-wide evidence access is genuinely intended: record that decision in an ADR and state it in the organizational data-access documentation, so it is an accepted risk rather than an oversight.
Required tests
Functional test: a department-restricted user requests the file_reference id of an out-of-scope record’s attachment → expect 404. Add the equivalent for the controlled-copy and export download paths. Extend RolePrivilegeFlowTests, which already establishes scoped users and asserts SCOPE-001.

Design assessment

Authentication. JWT bearer with issuer, audience, lifetime and signing key all validated and a 1-minute clock skew; Jwt:Secret absent aborts start-up. MapInboundClaims = false keeps claim names verbatim, so what is issued is what handlers read. MFA enrollment and confirmation exist with a gate middleware; a separate signature PIN backs the e-signature ceremony. Refresh follows ADR-0009: rotating httpOnly Secure SameSite=Strict cookie scoped to Path=/api/auth, with reuse-detection family revocation.

Authorization. Three cooperating layers. (1) A framework fallback policy requiring an authenticated user on every endpoint unless explicitly anonymous. (2) 144 [RequirePermission] action gates plus 57 controller-level [Authorize], with roles centralized in Roles.cs and permissions in PermissionCatalog. (3) AuthorizationBehavior in the MediatR pipeline, which fails closed: a command with no policy attribute is denied with AUTHZ-000 rather than allowed, an unknown permission key is denied with AUTHZ-008, and CommandPolicyTests makes “every command declares exactly one policy” a build-breaking rule. That is deny-by-default implemented as a mechanical property rather than a convention.

Session and privilege freshness. ActiveSessionMiddleware re-reads the account on every authenticated request, denying deactivated accounts (AUTH-006) and changed roles (AUTH-007), and re-resolving privileges from the database rather than trusting token claims. Revocation is therefore immediate — the control that keeps SEC-002 from being a blocker.

Gap. Queries are deliberately not gated in the pipeline (“read authorization stays at the controller — auditors must read”). That is a coherent decision, and the controller gates are substantial, but it means read authorization has no defence in depth: a controller action that forgets its attribute is protected only by the authentication fallback. The command side has a CI gate preventing exactly that class of omission; the read side does not. Recommended: extend the snapshot/CI gate to assert every query-serving action carries a permission attribute or an explicit, reviewed exemption.

21 · Observability and operational assessment

Observability. OpenTelemetry traces span HTTP → MediatR → EF/Npgsql → outbox and jobs, with traceparent persisted on outbox rows so a trace survives the asynchronous boundary — a detail often missed. Health and metrics endpoints are filtered out of traces to keep probe noise from the store. Production logging is structured JSON with scopes; OTLP export activates when Otlp:Endpoint is configured. Every response carries X-Correlation-Id (verified) and every problem+json carries traceId and correlationId (verified). LoggingBehavior emits request name, tenant, actor, elapsed time and outcome, explicitly never payloads; a search for credential-bearing log calls found none, and FieldChangeInterceptor redacts password/secret/pin/hash/token values before they reach the ledger. Gaps: /metrics is unauthenticated (SEC-001); trace sampling is unconfigured (all traces exported, a cost rather than a correctness issue); alert and dashboard effectiveness could not be verified without a live environment.

Operations. /health/live is deliberately check-free so a database outage recycles traffic rather than the process, and /health/ready is PostgreSQL-backed — both verified 200 with a bare “Healthy” body that leaks nothing. Both are anonymous and exempt from rate limiting, which is correct for probes. Resilience: Npgsql retry and command timeouts; advisory-lock leader election so sweeps do not overlap; outbox claim leases with bounded backoff and dead-lettering; deferred start-up seeding that retries instead of crash-looping when the database is cold. The backup/DR runbook is a genuinely strong artefact — RPO ≤ 5 min via continuous WAL archiving, RTO ≤ 4 h, daily/weekly/monthly retention with a 7-year floor, AES-256 at rest, off-site replication and quarterly documented drills — but no drill or restore evidence was supplied, so restore capability is documented, not demonstrated (NOT VERIFIED). The DatabaseRoleGuard deserves particular note: Production refuses to start if the connection role is SUPERUSER, has BYPASSRLS, or owns the tables — the deployment gate that makes the RLS story credible rather than aspirational, and its premise was confirmed here against the live role.

24 · Recommended implementation sequence

  1. Decide the two questions that change the work — is this a multi-tenant product (CLASS-001), and is branch/department a security boundary (ACCESS-001/003)? Both are answerable in a short conversation and both change the remediation scope.
  2. Prove or fix ACCESS-001. Write the scoped-user file-download denial test first. If it passes, the blocker dissolves and the remaining work is documentation. If it fails, fix it before release.
  3. Ship the one-line security corrections — Jwt:ExpiryMinutes: 15 with a ConfigGuard ceiling (SEC-002), the export permission gate (ACCESS-002), and real AllowedHosts (SEC-003). Low risk, immediate benefit, no design work.
