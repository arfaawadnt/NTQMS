01 Objective, scope & inputs

Verify how closely NT.QMS complies with the Enterprise Application Architecture checklist, using concrete evidence.

6-project Clean-Architecture solution + 5 test projects; EF Core configs & 40+ migrations; live PostgreSQL 17 dev DB; Angular 18 SPA; docker-compose.yml + Dockerfile; CI workflow; deploy/ runbooks; docs/validation/ CSV set + architecture markdown.

Executed this session (asserted as fact, not inference): Release build succeeded; ~270 backend + 37 frontend-unit + 3 Playwright e2e tests passed; migrations applied to real PostgreSQL 17; RLS & signed-record-immutability integration tests executed and passed.

Artifacts NOT provided

NOT VERIFIED: Enterprise_Application_Development_Standard.txt was not supplied — audited against the checklist in the prompt, which encodes those requirements.

No production runtime/telemetry, no penetration test, no load test, no formal ADR repository, no published OpenAPI artifact.

Assumptions & open questions

ASSUMPTION: the checklist is the authoritative standard absent the .txt. ASSUMPTION: production runs the least-privilege qams_app role (RLS relies on it).

OPEN QUESTION: intended production replica count (single-instance is currently implicit). OPEN QUESTION: is the analyst-can-delete-study-readings authorization intentional?

Stack deviations from the checklist's assumptions (verified): no Hangfire (background work is custom BackgroundService + transactional Outbox); no SignalR (Category 12 → Not Applicable); no Serilog/OpenTelemetry (default logging — a real observability gap); no Polly/rate-limiter; Angular 18 not 19.

02 Executive summary

NT.QMS is a well-engineered, DDD-faithful modular monolith whose regulated-domain core is production-grade: a genuinely rich domain layer with in-domain invariants and guarded state machines; two independent, fail-closed tenant-isolation layers (EF global filter + FORCED PostgreSQL RLS) backed by a least-privilege role and passing cross-tenant denial tests; a SHA-256 hash-chained append-only audit trail with DB-trigger signed-record immutability; and dual-factor (password + PIN) Part-11 e-signatures. Clean-Architecture boundaries are enforced by NetArchTest as CI gates. This is verified in code and, for the highest-risk controls, at runtime.

The gaps are concentrated in the operational and runtime-robustness dimensions that a regulated multi-tenant SaaS needs before an unconditional production release: there is no distributed tracing, log aggregation, or metrics/alerting; no optimistic-concurrency control on any aggregate (silent lost-update risk); the Outbox has no dead-letter or backoff and its documented retention job does not exist; the health endpoint never tests the database; the background workers implicitly assume a single replica; and there is no rate limiting or security-header/CSP hardening at the application layer. None are critical-severity or expose data across tenants, but several are legitimate production blockers.

07 Domain & architecture assessment

Categories 2–4. Compliance 68% / 100% / 92%.

Strengths

  • Domain project references only SharedKernel — zero framework/EF/MediatR packages; enforced by NetArchTest (ARCH-001, ARCH-003).
  • Rich aggregates: private setters, factories, guarded state machines, invariants in-domain, value objects, domain events over a transactional outbox; SoD baked into AggregateRoot (DOMAIN-001…006).
  • Entities never exposed via API — separate Contracts DTOs, enforced by an architecture test (DOMAIN-007). No dependency cycles (ARCH-007). No god classes (ARCH-010).

Gaps

  • DOMAIN-009 (High): no optimistic-concurrency token on any aggregate — see blocker.
  • ARCH-004 (Medium): modular-monolith boundaries are conventional; one shared IAppDbContext exposes every DbSet, so cross-module access isn't compile-prevented.
  • ARCH-005 (Medium): no API/contract versioning strategy. ARCH-006 (Low): no ADR record set (rationale lives in comments/markdown).
  • ARCH-002 (Low): Application couples to EF Core via DbSet in the persistence port (a deliberate, tested Clean-Architecture convention).

08 Database & tenant-isolation assessment

Categories 8 & 9. Compliance 97% / 85%. No cross-tenant exposure found.

Strengths

  • Two enforcing isolation layers: EF global filter (applied by convention, fail-closed) + ENABLE+FORCE ROW LEVEL SECURITY with USING/WITH CHECK reading per-connection GUCs; verified to extend to every table added after activation (TENANT-002/003, DB-014).
  • Tenant id from JWT claim only across all 37 controllers — no body/route/query binding (TENANT-001). Connection-pool re-stamps GUC on each open (TENANT-005). Background jobs use scoped Elevate() (TENANT-006).
  • UUIDv7 PKs (ValueGeneratedNever), tenant-scoped unique indexes, decimal precision, UTC DateTimeOffset, no generic repository, no IQueryable leak, append-only hash-chained ledgers + frozen-record triggers (DB-002/004/007/008/013/015/016).

Gaps

  • DB-005 (Medium): zero domain CHECK constraints — enum/range/date invariants live only in code, not at the DB "last line of defense".
  • DB-009 (High): no concurrency token (blocker). MSG-007 (Medium): Outbox retention job is documented but not implemented → unbounded growth.
  • TENANT-004 (operational): RLS only bites when prod connects as qams_app — must be verified at deploy.

09 Security & STRIDE assessment

Categories 7 & 16. Compliance 90% / 58%.

Strong (Spoofing/Tampering/Repudiation/Elevation)

  • Full JWT validation (issuer/audience/signature/lifetime, tight skew, fail-fast secret); deny-by-default fallback; per-tenant TOTP MFA + enrollment gate; live session/role revocation (SEC-001/002/004/005).
  • Unified strong-password policy; user-enumeration-resistant errors; PBKDF2 hashing (SEC-006/007).
  • Repudiation covered by the hash-chained audit trail + append-only grants + dual-factor e-signatures (SEC-016). Parameterized EF everywhere (SEC-014). DTO binding, not entities (SEC-015).

Gaps (Info-disclosure / DoS)

  • SEC-011 (Medium): no security headers (HSTS/CSP/X-Frame/X-Content-Type). SEC-017 (Medium): JWT stored in localStorage — XSS-exfiltratable without a CSP.
  • SEC-013 (High): no application-layer rate limiting (only per-account lockout) → brute-force/DoS exposure on /api/auth/* and the password+PIN publish endpoint.
  • SEC-010 (Low-Med): no CORS policy (defensible for the same-origin SPA, but undocumented). SEC-012: in-app HTTPS/HSTS delegated to the proxy — must be confirmed.
  • SEC-003 (Low): analytical-study sub-resource DELETEs inherit only class-level [Authorize] — an Analyst can delete study readings within their own tenant; confirm against the threat model.

10 API, CQRS & validation assessment

Categories 5, 6, 14. Compliance 68% / 52% / 72%.

Strengths

  • Textbook CQRS — commands mutate one aggregate & return refs, queries project to DTOs with AsNoTracking, controllers are pure dispatchers; validation runs before every handler (CQRS-001/002, VAL-001).
  • Central exception handler maps coded DomainExceptions to correct RFC-7807 statuses (401/404/409/422); stable machine-readable error codes; no stack-trace/SQL/secret leakage (VAL-002/004, API-007).

Gaps

  • API-002 (High): no rate limiting. API-001 (Medium): no API versioning. API-006 (Low-Med): no correlation IDs.
  • VAL-003 (Medium): concurrency conflicts unrepresented (DbUpdateConcurrencyException→500). API-003 (Med): ProblemDetails emitted as application/json not problem+json; middleware writes anonymous error objects (shape drift).
  • API-004 (Medium): list endpoints use a silent .Take(500) cap, not real pagination. API-005 (Medium): file download echoes stored content-type without attachment disposition + no type allow-list (stored-XSS vector).
  • CQRS-003/004 (Medium): authorization / idempotency / transaction / performance pipeline behaviors absent (authorization deferred to "Phase 1" in code — currently attribute-only, and some commands have no role gate).

Strengths

  • Exemplary DR runbook (RPO ≤5 min PITR / RTO ≤4 h, off-site AES-256, drills, hash-chain restore verification) + backup/restore scripts (OPS-012). Clean secret externalization + centralized roles (CFG-003/004).

Gaps

  • OPS-008 (High, blocker): readiness doesn't test the DB. OPS-009 (Medium): no Npgsql retry / circuit breaker. OPS-010 (Medium): no rate limiting.
  • CFG-001/002 (Medium): options are hand-rolled with silent fallback; connection string not validated at startup. DEPLOY-002 (Medium): container runs as root. DEPLOY-003 (Medium): no resource limits; compose is dev-DB only.

16 Recommended implementation sequence & required ADRs

Sequence

  1. Confirm the qams_app production role & readiness health (cheap, highest safety) — TENANT-004, OPS-008.
  2. Decide replica topology: enforce single-instance now, or add SKIP LOCKED/leader election — OPS-002.
  3. Add optimistic concurrency (xmin) + 409 mapping — DB-009.
  4. Harden the Outbox: dead-letter, backoff, dedup, retention — MSG-004…007.
  5. Observability baseline: JSON logs + OTel + correlation IDs + metrics/alerts — OBS-001…003.
  6. Edge hardening: rate limiting + security headers/CSP — SEC-013/011.
  7. API polish + config validation + container hardening + the test-coverage gaps.

Required ADRs (currently undocumented decisions)

  • JWT stored in localStorage (risk-acceptance vs httpOnly cookie).
  • Trigger-based immutability instead of version-token concurrency — and the plan to add both.
  • Single-threaded in-process Outbox + implicit single-replica topology.
  • Application coupling to EF Core DbSet in the persistence port.
  • Same-origin deployment assumption (no CORS by design).

PRODUCTION DECISION: APPROVED WITH CONDITIONS
