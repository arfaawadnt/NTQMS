01

Executive Summary

NT.QMS is a genuinely capable, well-architected quality-management platform. Every module inspected has a real domain model, API and user interface — there are no hollow or mock screens — and several regulated-record controls (a hash-chained audit trail, a dual-component electronic signature, server-side time, and consistent sign-off freezing) are implemented to a standard rarely seen at this stage. However, as a computerized system for GxP use it is pre-validation, and three critical, go-live-blocking defects were confirmed. The functional breadth must not be mistaken for compliance readiness: per this audit's scoring rules, unresolved critical findings override any favourable functional percentage.

Critical 1 — Tenant isolation is not enforced at the database. PostgreSQL Row-Level Security policies exist on 53 tables but are dormant: the application never sets the app.current_tenant session variable, sets no FORCE ROW LEVEL SECURITY, and connects as the table-owning role — all three independently defeat RLS. Isolation currently rests solely on an in-process EF query filter, which 25+ IgnoreQueryFilters() code paths bypass with no database backstop. For a multi-tenant regulated system this is a data-integrity and confidentiality blocker.
Critical 2 — Regulated business records are database-editable. Append-only triggers and least-privilege protect the four audit.* ledger tables, but no equivalent protection exists on the qams.* tables holding signed studies, documents, NCs and archives. A holder of the application's database role (or a DBA) can UPDATE/DELETE a signed-off record via raw SQL — bypassing every domain guard and leaving no trail, since the change-ledger only observes EF-mediated writes. The intended least-privilege runtime role is described in a code comment but is not codified in any migration (zero GRANT/REVOKE).
Critical 3 — No computerized-system-validation evidence exists. There is no Validation Master Plan, URS, functional/design specification, requirements-traceability matrix, IQ/OQ/PQ, UAT, formal risk assessment or validation summary report. The architecture/sizing Markdown documents are engineering artefacts, not approved validation deliverables. The system is formally unvalidated and cannot be released for regulated production use on that basis alone (21 CFR Part 11 §11.10(a); Annex 11 §4).

Balance of evidence. The audit-trail and electronic-signature subsystems, the sign-off-freeze immutability across all twelve analytical study aggregates, server-UTC contemporaneity, fail-closed tenant/actor attribution, deny-by-default authorization, account lockout, PBKDF2 hashing, and ~203 backend tests (including a hash-chain tamper test and a dual-component signing test) are real strengths. The gaps are concentrated in (a) database-layer enforcement of controls that today live only in application code, (b) enforcement of multi-factor authentication and segregation of duties, and (c) the entire formal validation lifecycle.

Recommended decision: Production release prohibited; UAT may continue. The system is a strong conditional candidate — the three blockers are addressable with focused engineering (activate RLS, harden the database role, execute a CSV) rather than redesign.

Application Architecture & Module Inventory

Clean/DDD architecture with CQRS (MediatR), EF Core 9 on PostgreSQL (snake_case, UUIDv7 keys), and an Angular 18 standalone/signals frontend. Cross-cutting compliance services are centralized behind single application ports — identity/RBAC, electronic signature, audit-trail/field-change ledger, security events, notifications, attachments and reporting each have one implementation, not per-module copies. This is an architectural strength and materially reduces Part 11 risk surface.

Repeated & Duplicate Modules

No true duplicates found. Each navigation item maps to a distinct aggregate, controller and UI. Cross-cutting services (identity, e-signature, audit trail, notifications, attachments, reporting) are single centralized implementations — not re-implemented per module. This is a notable strength versus typical enterprise QMS builds.

Watch items (not defects):

  • Improvement-event chain — Feedback → Complaint → Nonconformance are three deliberately-separate aggregates with escalation links; correct modelling, but confirm users are guided to the right entry point so the same dissatisfaction is not opened in two places.
  • Analytical study surface — a generic ValidationStudy coexists with 12 specialised study aggregates. Confirm the generic study is still needed and is not a thinner variant of the specialised ones (menu-bloat / wrong-module-selection risk).
  • Risk linkage appears in the risk register and is referenced by change requests and context issues — correct cross-linking, not duplication.

Electronic Records & Signatures (Part 11 / Annex 11)

Audit trail Strong

  • Two computer-generated mechanisms: a field-change ledger (EF SavingChanges interceptor, same transaction) and a SHA-256 per-tenant hash-chained event trail with an independent verifier.
  • Captures user, server-UTC timestamp, action, entity, old & new value; credentials redacted at capture.
  • Append-only enforced by DB triggers on all four audit.* tables; ledger self-excluded from capture.
  • Gaps: no reason-for-change field (F-06); no transaction/correlation id; no CSV/PDF export (F-13); completeness depends on EF — out-of-band SQL writes leave no trail (tied to F-02).

Electronic signatures Strong

  • Two components re-verified at signing — account password + separate e-signature PIN (§11.200).
  • Records signer identity, server-UTC, and human-readable meaning; permanently bound to the record via SHA-256 content hash + subject reference (cannot be transplanted).
  • Rows immutable (append-only trigger); segregation of duties enforced for document approval (author≠approver).
  • Gaps: failed signing attempts not logged/rate-limited (F-08); post-signature freeze relies on each aggregate's state machine — not a system-wide invariant, and a later edit does not auto-invalidate an existing signature (F-05 related).
Record protection is the weak point (F-02). Signatures and audit rows are DB-protected; the signed business records they attest to are not. Because tamper-evidence is generated by the EF layer, a direct-SQL change to a signed qams.* record is both possible (no trigger/least-privilege) and invisible (no ledger row). This undermines the reliability of the otherwise-excellent signature/audit design.

Security & Access Control

Strong controls

  • Deny-by-default authorization (global fallback policy); role gates on all endpoints.
  • PBKDF2-HMAC-SHA256 password hashing; account lockout (5 attempts / 30 min); password aging (90 d) & reuse ban (last 5).
  • Tenant resolved only from the validated JWT claim — headers/query spoofing explicitly banned.
  • Fail-closed attribution: unscoped rows are rejected (TENANT-000), not silently persisted.
  • Soft deactivation (no hard user delete) preserves the Part 11 trail.

Weaknesses

  • Tenant RLS dormant (F-01) — GUC unset, no FORCE RLS, app runs as table owner; single-layer app isolation with IgnoreQueryFilters() bypass surfaces.
  • MFA not enforced (F-04) — TOTP is opt-in even for TenantAdmin/PlatformAdmin.
  • SoD absent in analytical sign-offs (F-05).
  • No JWT revocation / idle-timeout / refresh (F-07); deactivated token valid ≤120 min.
  • Password policy: no complexity/breach check; min length inconsistent (10 vs 12) (F-15).
  • Dev credentials (JWT secret, DB & platform-admin passwords) committed in appsettings.Development.json (F-17).

Integration & Data Migration

  • Interfaces: the product exposes a REST API and a CSV/analyzer importer with per-row validation. No live LIMS/LIS/ERP/HL7/identity-provider integration was evidenced; lab-operational functions assumed external must be delivered via a controlled, validated interface with error handling, reconciliation and traceability — none of which is yet specified or tested.
  • Error handling / exception queues: an outbox pattern drives domain events and the audit chain; interface error-queue/reconciliation for external systems is Not verified (no external interface present).
  • Data migration: greenfield schema (26 EF migrations); no legacy-data migration in scope, so migration validation is N/A today — but must be planned before any production data load, restore or tenant import.

Remediation Roadmap

Immediate containment (before further UAT with real data)

  • F-01 Activate tenant isolation: introduce a low-privilege non-owner runtime DB role, add FORCE ROW LEVEL SECURITY, and set app.current_tenant per connection/transaction via a DbConnection interceptor. Add automated cross-tenant denial tests. (Evidence: passing RLS integration tests; role privileges.)
  • F-02 Codify least-privilege grants and add DB-level immutability on signed/closed regulated tables; prohibit direct production DB writes by procedure. (Evidence: migration with GRANT/REVOKE + triggers; DBA SOP.)
  • F-17 Rotate and remove committed dev secrets.

Before UAT sign-off

  • F-04 Enforce MFA for privileged roles. F-05 Add SoD guards to analytical sign-offs and NC verify. F-06 Capture reason-for-change on all regulated voids/edits; implement QC target effective-dating.
  • F-09 Add PostgreSQL integration tests (RLS, deletes, migrations, e-sig, audit) to CI.

Before production release (go-live blockers)

  • F-03 Execute the CSV lifecycle: approved VMP, URS, FS/DS, risk assessment, RTM, IQ/OQ/PQ, UAT, and validation summary — traced to executed evidence on the qualified target platform.
  • F-07 Token revocation/idle-timeout. F-08 Log/limit failed signings. F-10 Backup-restore & DR test. F-11 Close priority governance gaps (quality policy, read-and-understand, legal hold, PIR).

Within 30–90 days / continual improvement

  • F-13 trail export · F-14 mandatory archive snapshot + hold · F-15 password policy · F-16 externalize controlled parameters · F-18 frontend/e2e coverage · data-driven privilege matrix · distinct deviation/OOS/OOT event types · periodic access review · shared action-tracker engine.
