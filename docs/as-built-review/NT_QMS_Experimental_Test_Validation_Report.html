1 · Executive Summary

This engagement performed a real, evidence-based end-to-end test of the live NT.QMS application: 106 test cases, all executed, covering every one of the 48 navigation pages (mapped from the SPA's own menu). Two isolated test tenants were provisioned through the platform-admin API; multiple users with distinct roles were created; and genuine records were created and driven through their workflows — including all 12 ISO 17025 analytical-study types, method comparison (Deming/Passing-Bablok to sign-off), statistical QC, management review, tasks, PT, archiving, organizational context, and the reporting/compliance dashboards. Every data-changing action was validated at three layers: the REST API response, the PostgreSQL record, and the audit trail / electronic-signature ledger; report figures were reconciled against source records. The core battery was also re-executed against the live arfa (Arfa Lab) tenant (§6b), producing identical results.

Overall posture is strong. The platform demonstrates mature quality/compliance controls: enforced Segregation of Duties (author ≠ reviewer; preparer ≠ signer), 21 CFR Part 11 electronic signatures bound to a content hash, a hash-chained tamper-evident audit log, comprehensive field-level change auditing with before/after values, robust multi-tenant isolation, safe input handling, and correct role-based authorization.

Release is Conditionally Ready. No Critical defects and no data-loss or cross-tenant exposure were found. One High, two Medium and three Low findings should be resolved before UAT sign-off — chiefly (a) NTQMS-FND-001 (High), a systemic pattern of unhandled 500s on out-of-domain enum / unmet-precondition input across at least four create endpoints; (b) silent coercion of out-of-range document review-cycle values; and (c) analytical sign-offs not written to the central electronic-signature ledger.

Key strengths (positive controls confirmed by execution)

  • Segregation of Duties — document author blocked from reviewing own doc (SOD-DOC-001); record preparer blocked from signing off analytical study (SOD-AQ-001).
  • Electronic signature — document publish required password + PIN re-authentication and produced a signature bound to the file SHA-256 content hash.
  • Tamper-evident audit — audit.audit_trail is a sequenced hash chain (prev_hash → entry_hash verified); audit.field_change logs Created/Modified with old→new values, actor and timestamp for every entity, including child rows.
  • Multi-tenant isolation — every cross-tenant object reference (document, file, NCR, retire, list, search) returned 404 / empty for the foreign tenant.
  • Authorization — least-privilege Analyst correctly denied (403) admin operations; generic 401 on all bad-credential variants (no user enumeration); tampered JWT rejected.

Release recommendation

CONDITIONALLY READY for the next testing stage (UAT). Resolve the 3 Medium findings before UAT approval; the 2 Low findings can be scheduled. No data-integrity, cross-tenant, or audit-loss defect was observed.

14 · Recommendations

Immediate hotfix

  • NTQMS-FND-001 (High) — Systematically add application-layer enum/domain and precondition validation to all create/update endpoints so invalid input returns 400/422, never a 500 from a DB CHECK or unhandled precondition. Confirmed on 4 endpoints (reference-standards, org-context issues, archives, test-authorizations) — treat as a codebase-wide sweep. Add a global DbUpdateException/constraint→ProblemDetails handler as a safety net.

Before UAT approval

  • NTQMS-FND-002 (Med) — Enforce server-side bounds on reviewCycleMonths (1–120). Reject out-of-range input with 400 instead of silently coercing to 24.
  • NTQMS-FND-003 (Med) — Write analytical/study sign-offs (and any credential-gated sign-off) to audit.electronic_signature with signed meaning + content hash, consistent with document publish, for uniform Part 11 evidence.

Before production

  • NTQMS-FND-004 — Make /documents/{id}/signatures (and similar sub-resources) 404 on a foreign/unknown parent id.
  • NTQMS-FND-005 — Reject triage without an assignee (or omit the field) rather than storing an all-zero GUID in AssignedTo.
  • NTQMS-FND-006 — Clarify the outlier-screening create contract (name the dataset element type and the required r field) and return a descriptive validation message.
  • Resolve the reference-data (LOV admin), controlled-records/forms, and quality-manual page endpoints so those 3 remaining pages can be fully exercised.

Recommended improvements / further testing

  • Drive full CAPA closure (rca→verify→confirmEffectiveness) and the failed-effectiveness reopen path.
  • Execute the remaining ~20 analytical sub-study modules and the module-interaction chains (NCR→CAPA, complaint→investigation, audit-finding→NCR).
  • Add UI-layer (browser) regression for accessibility, RTL Arabic, and localization (en/ar/fr) — not covered here.
  • Confirm account lockout thresholds live (failed_login_attempts/locked_until_utc columns exist; not exercised to avoid locking working accounts).

15 · Conclusion

NT.QMS is a well-architected, compliance-oriented QMS. Executed testing across ~35 pages confirms that its most safety-critical controls — segregation of duties, electronic signatures with content binding, tamper-evident and field-level auditing, strict multi-tenant isolation, and reporting that reconciles to source records — function correctly against the live database. The one High finding is a systemic error-handling pattern (unhandled 500s on invalid input), not a data-loss or security-exposure defect; the remaining findings centre on input-validation hardening and signature-ledger consistency.

Recommendation: CONDITIONALLY READY for UAT. Fix NTQMS-FND-001 (High, systemic 500s) and the two Medium findings before UAT sign-off; schedule the three Low findings. No Critical defect, data-loss, or cross-tenant exposure was found, so none blocks progression once FND-001 is addressed.
