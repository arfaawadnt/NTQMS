2 · Audit Scope & Limitations

Reviewed (objective evidence obtained)

  • Full PostgreSQL schema — 100 tables across qams, saas, audit, read, public.
  • Tenant-isolation implementation (Row-Level Security policies + role attributes) — tested empirically.
  • Audit-trail, electronic-signature, field-change and security-event structures and live contents.
  • Immutability / append-only enforcement (triggers + privilege grants) — tested empirically.
  • RBAC model (5 roles, 171 permission keys), access-control columns, deployment topology, appsettings.json.

Not available (drives most “Not Verified” results)

  • No validation package on host: no VMP, URS, FS/DS, risk assessment, IQ/OQ/PQ, traceability matrix, test evidence, or validation summary.
  • No application source code on host (only PowerShell deploy assets).
  • No approved SOPs / quality manual / policies to test procedure-controlled requirements.
  • Near-zero production records — “used in production” and “effective operation” cannot be demonstrated (see §3).
  • API route inventory not fully enumerable (Swagger disabled in production). No backup/restore, DR or penetration-test evidence supplied.

Effect: where a control was provable at the database layer it is reported as evidenced; where a control depends on application logic, procedures, or usage that could not be observed, it is Not Verified — not assumed conforming (audit rule 21.7).

3 · Executive Summary

The single decisive theme: the software is architecturally strong, but operational and validation evidence is near-zero. Both halves are true simultaneously and together they set the readiness verdict.

Strengths — genuinely enforced controls (tested)

  • Hash-chained, append-only audit trail (prev_hash→entry_hash) enforced by both least-privilege grants and BEFORE UPDATE/DELETE triggers — tamper attempts by the app role return permission denied.
  • Forced Row-Level Security on 93 tables; app roles are non-superuser / non-bypassrls, so tenant isolation holds at the database.
  • Immutability triggers on the analytical-validation records; no delete path for regulated data (app role can delete only 3 transient tables).
  • Fine-grained RBAC — 171 permission keys across 31 namespaces; 5 roles with real least-privilege differentiation. Refresh-token reuse detection observed.
  • Comprehensive ISO 15189/17025 analytical suite (Westgard QC, proficiency testing, uncertainty budgets, method comparison, reference intervals).

Blocking gaps — why it is not production-ready for regulated use

  • No validation evidence (F-06) — no VMP/URS/IQ/OQ/PQ/traceability. The system cannot be shown fit for its intended use. Critical
  • Electronic signatures never used (F-04) — 0 signatures ever created; signing integrity is unproven in operation. Major
  • Core QMS records not DB-immutable after approval (F-01) — post-approval integrity relies on app logic only. Major
  • RLS bypass reachable by the app role (F-02) — a qams_app session can set app.bypass_rls='on' itself; an injection flaw could cross tenants. Major
  • Audit capture is application-layer (F-05) — direct database edits are not recorded in the trail. Major

10 · 21 CFR Part 11 / Annex 11 — Electronic Records & Signatures

Applicability is conditional on a predicate rule (Not Verified). Assessment is of technical capability + operational evidence.

Access controls — mostly evidenced

  • ✓ Unique user IDs; PBKDF2 password hashing; password policy (90-day age, 5-history); lockout columns; MFA columns present.
  • ✓ Session control: JWT 120-min; refresh sessions with token-reuse detection (observed in security events).
  • △ Periodic access review not executed (M-02); SoD rule-set enforcement Not Verified.

Electronic signatures — capability present, operation unproven

Schema supports the mandatory manifestations: signer_display (name), meaning, signed_at_utc (time), and subject_ref + content_hash (permanent, tamper-evident link to the signed content). However the table has 0 rows — so identity verification at signing, re-authentication, failed-attempt capture, non-transferability, “record reviewed before signing,” and “post-signature change invalidates prior approval” are all Not Verified.

Audit trails — strong and evidenced

  • ✓ Computer-generated, timestamped, append-only enforced by BOTH grant (INSERT/SELECT only) and BEFORE UPDATE/DELETE triggers (tested: app-role UPDATE/DELETE → permission denied).
  • ✓ Tamper-evident hash chain (prev_hash→entry_hash, per-tenant sequence; 0 null hashes, chain intact).
  • ✓ field_change captures actor, old value, new value, reason, timestamp (773 rows, working).
  • △ Human-readable review/export & periodic review operationally Not Verified (M-04).
  • △ Coverage limit: trail reflects application actions only; direct DB changes are invisible (F-05).

12 · Security & Access Control

  • Authentication: JWT (120 min), PBKDF2 hashing, password aging + history, lockout, MFA columns — strong design.
  • Authorization: 171 permissions across 31 namespaces; 5 roles with real least-privilege differentiation (Tenant Admin 171 → Quality Manager 165 → Dept Head 90 → Analyst 65 → External Auditor 47, read-oriented).
  • Tenant isolation: forced RLS — strong, except the bypass switch (F-02) and user_account RLS off (F-03).
  • Transport: TLS at IIS; API bound to loopback only — not externally reachable except via proxy.
  • Not Verified: penetration test, UI session-timeout behavior, emergency/service-account governance, IdP/SSO.
